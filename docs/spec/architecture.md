# Архітектура проєкту (Architecture)

Проєкт SubOptima побудований за принципами **Гексагональної архітектури (Ports and Adapters)**. Цей підхід забезпечує повну ізоляцію бізнес-логіки від зовнішніх фреймворків, баз даних та інтерфейсів користувача.

## 1. Структура Гексагональної архітектури

Система розділена на три основні шари:

1. **Доменне Ядро (Domain / Models):** Містить чисті сутності бізнесу (`User`, `Service`, `UserSubscription`, `UsageFeedback`). Вони не знають ні про базу даних, ні про API.
2. **Порти (Ports) та Use Cases:** Інтерфейси абстрагують роботу зі сховищем (наприклад, `IUserRepository`). Use Cases (наприклад, `GenerateRecommendationsUseCase`) реалізують бізнес-правила (нечітку логіку) і взаємодіють лише з Портами.
3. **Адаптери (Adapters):** * *Primary Adapters (Вхідні):* FastAPI Routers та Jinja2 шаблони. Вони приймають запити користувачів, валідують їх через Pydantic DTOs і викликають Use Cases.
   * *Secondary Adapters (Вихідні):* Класи, що реалізують інтерфейси Портів для конкретних технологій (MongoDB через `pymongo` або In-Memory словники).

## 2. Dependency Injection (Ін'єкція залежностей)

Ключовим механізмом зв'язування шарів є ін'єкція залежностей, яка налаштована у файлі `src/main.py` за допомогою системи `Depends` від FastAPI.

**Як це працює:**
1. При старті програми зчитується `.env` файл (`STORAGE_TYPE`).
2. Залежно від конфігурації, `main.py` ініціалізує або `MongoRepository`, або `InMemoryRepository`.
3. Ці конкретні екземпляри (синглтони) передаються у функції-провайдери (наприклад, `get_subscription_repository()`).
4. Коли роутер приймає HTTP-запит, FastAPI автоматично "впорскує" ці репозиторії у відповідний Use Case. 

Це дозволяє нам тестувати бізнес-логіку або переходити на іншу базу даних без жодних змін у коді самих Use Cases.
