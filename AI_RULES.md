# Глобальні правила розробки для проєкту SubOptima

- **Архітектура:** Ми використовуємо Гексагональну архітектуру (Ports & Adapters). Заборонено імпортувати адаптери (`src/storage/`) всередину доменних моделей (`src/models/`) або логіки портів.
- [cite_start]**Інтерфейси:** Заборонено генерувати сервіси, use-cases або репозиторії без попереднього опису їхніх інтерфейсів (абстрактних класів) у `src/services/ports/`.
- [cite_start]**Бази даних:** Заборонено використовувати зовнішні БД чи реальні мережеві API під час виконання юніт-тестів. [cite_start]Завжди використовуйте імплементації з `src/storage/in_memory/`.
- **Тестування:** Ми використовуємо підхід TDD там, де це можливо. [cite_start]Кожна нова бізнес-функція повинна супроводжуватися відповідними тестами в директорії `tests/`.

# Стратегія тестування (Testing Strategy)

- [cite_start]**Цільові метрики:** Мінімум 200 модульних та інтеграційних тестів, загальне покриття коду (Code Coverage) >= 70%.
- [cite_start]**Фреймворк:** `pytest` із плагіном `pytest-cov` для аналізу покриття гілок логіки.
- [cite_start]**Ізоляція:** Для ізоляції шарів бізнес-логіки використовуйте Mock-об'єкти (`unittest.mock` або `mockito`) замість реальних викликів інфраструктури.
- [cite_start]**Генерація даних:** Для тестів аналітики за 12 місяців використовуйте автоматично згенеровані тестові дані (fixtures), імітуючи різні патерни поведінки користувачів (активні користувачі, користувачі з "мертвими" підписками).
